# OWASP Top 10 (2025) review and hardening

Date: 2026-11-17 · Size: project · Status: draft for approval

## Why
The user is **selling the app to their company**; security comes first. This is piece 2 of 3 of their security push
(1 = safe page building, done; 3 = two-step login, next). The company will judge the app against the current
OWASP Top 10, which is the **2025** list; SECURITY.md still maps to 2021.

**Assumption (user: "assume the strictest case"):** the app is **reachable from the internet**, not only from the
office / VPN.

## Goals
- Go through **every 2025 category** against the code and fix what falls short, test first.
- Add a **change history**: every create / update / delete of a vessel, service, booking, master-data value, exchange
  rate and user role is stored in the database with who, when, from which address, and the **old and new values**;
  admins can read it on a new page; nobody can edit or delete it through the app. (User picked this from the ARKAS
  2027 preview; it also serves A09.)
- Rewrite SECURITY.md §2 for the 2025 list, each row saying what the app does, how it is tested, and what is left to
  the people who deploy it.

## Non-goals
Two-step login (piece 3); the other preview ideas (frozen exchange rate per service, service status, billing basis,
accounts review — next, after this); a penetration test (recommended in SECURITY.md, done by others); visual changes
beyond the History page.

## Anti-goals
- Security theatre: a control without a test that proves it.
- Breaking what users do today (same screens, same roles, same data), or a fix that needs a new runtime service
  (Redis, a mail server) to keep working: anything external must be optional and degrade safely.

## Approaches
| | What | Trade-off |
|---|---|---|
| **A. Category-by-category review of the code, fixes test-first, fresh security reviewer at the end (chosen — the user handed me the how)** | One review pass per 2025 category with a written finding list; each fix has a failing test first | Thorough and provable; costs time |
| B. Add a dynamic scanner (OWASP ZAP) | Automated probing of the running app | Needs Java + a large download; finds a subset of what A finds; worth doing by the company's testers |
| C. Leave it to an external penetration test | Independent | Not something we can do; SECURITY.md recommends it |

## The review, per category (what is already known + what will be checked)
- **A01 Broken Access Control** (now includes SSRF): every endpoint's role / port scoping (already tested), plus the
  new History endpoint (admin only), CSV export, and direct object references in every `<int:pk>` route.
- **A02 Security Misconfiguration:** unexpected errors and unknown URLs must never show Django's debug or generic HTML
  pages to the API; production cookies get the `__Host-` prefix; `check --deploy` clean.
- **A03 Software Supply Chain Failures (new):** `requirements.txt` allows ranges (`Django>=5.2,<7.0`) with no hashes →
  a locked file with **exact versions and hashes** (`requirements.lock`, installed with `--require-hashes`), kept in
  step by a test; the vendored PDF.js is checked against a recorded **SHA-256**; `npm run check` keeps running
  pip-audit / npm audit.
- **A04 Cryptographic Failures:** HTTPS / HSTS / cookies / DB TLS (already); confirm no secret reaches logs or
  responses; password hashing settings.
- **A05 Injection:** ORM only, validators, CSV formula escaping, no HTML strings (piece 1) — re-check every input
  path incl. query parameters and headers.
- **A06 Insecure Design:** internet-facing ⇒ **rate limiting on the API** (not only on login): a per-user and
  per-address limit on writes and on CSV export, answered with 429, stored the same way as the login throttle
  (database, no new service).
- **A07 Authentication Failures:** lock-out, password rules, session expiry (already); check username enumeration
  (same answer and similar timing for unknown users), session rotation on login; MFA stays piece 3.
- **A08 Software or Data Integrity Failures:** the hashes from A03; the change history makes data changes traceable.
- **A09 Security Logging and Alerting Failures:** the change history (above); **alerting** — when lock-outs, denied
  requests or server errors pass a threshold in a time window, a single `sheet.alert` log record at ERROR level is
  written, and an **e-mail goes to the admins only if e-mail is configured** (`DJANGO_ALERT_EMAILS` + Django's e-mail
  settings); logs can also go to a rotating file (`DJANGO_LOG_FILE`).
- **A10 Mishandling of Exceptional Conditions (new):** every API error answers JSON (`{"error": …, "ref": …}`) with
  a short reference that also appears in the server log, never a stack trace; failures fail **closed** (a throttle
  or history-write error never lets a request through unrecorded); the front end shows the reference.

## Change history — shape
- Model `ChangeRecord`: `at`, `user` (FK, kept if the user is deleted → `SET_NULL` + `username` copy), `ip`,
  `action` (create / update / delete), `object_type`, `object_id`, `port`, `changes` (JSON: `{field: [old, new]}`;
  full snapshot for create / delete). No update / delete path in the app; Django admin read-only.
- Written in the **same database transaction** as the change, from one helper next to `api.audit` (if the write
  fails, the change fails).
- **History page** (admins only, sidebar item "History"): newest first, filter by date range, object type and user,
  paged like the other lists; shows field, old → new.

## Settled after the builder check (my calls — the user can overrule any)
1. **What the history captures:** model **signals** (post_save / pre-delete) with the current request carried in a
   context variable, so *every* path is recorded: API views, bulk add (one record per vessel), cascaded deletes (one
   record per deleted child: services, bookings, guests), the Django admin, and management commands (user shown as
   "system"). Updates store only the fields that changed.
2. **Immutability:** no edit / delete path in the app or the Django admin; on PostgreSQL a migration adds a
   **trigger that refuses UPDATE and DELETE** on the history table (SQLite skips it). **Kept forever** — no purge;
   if the company later wants a retention period, that is a separate, deliberate change.
3. **Lock file:** `pip-compile --generate-hashes` pins exact versions with the hashes of **every published file** of
   each version, so the same lock installs on Windows and Linux (and any CPU PyPI ships wheels for). Regenerated with
   one documented command; a test fails if `requirements.txt` and the lock disagree.
4. **Proxies:** a deploy check (`check --deploy`) **fails** when `DJANGO_BEHIND_PROXY=1` is set without
   `DJANGO_CLIENT_IP_HEADER`, because rate limits, lock-outs and history addresses would otherwise all see the proxy.
5. **`__Host-` cookies:** on in production; everyone signs in once more after the update; the app must be served
   from the root of its own host (written in the deployment checklist).
6. **Rate limits count requests, not rows** (a 200-row bulk add is one request). If the throttle store fails,
   **writes fail closed** (refused) and **reads fail open** (allowed), so a database hiccup never lets unrecorded
   writes through but doesn't blank the screens.
7. **Alert e-mails** go only to the addresses in `DJANGO_ALERT_EMAILS` (no mail is sent when it is empty).

## Testing
Backend tests per finding (each written to fail first); smoke test: admin sees History with the changes the run
made, port / read-only users don't see the page and get 403 from its API; `npm run check` green.

## Left to the builder
Exact thresholds for rate limits and alerts (reasonable defaults, overridable by environment variables); file
layout; the order of categories.
